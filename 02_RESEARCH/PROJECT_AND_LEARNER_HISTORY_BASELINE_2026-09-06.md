# W.I.S.D.O.M. Project and Learner History Baseline — 2026-09-06

**Status:** NON-OPERATIVE RESEARCH SYNTHESIS  
**Purpose:** establish a current history baseline for later educational analysis  
**Curriculum status:** none; this is research evidence and interpretation

## 1. Why this baseline exists

W.I.S.D.O.M. is being designed after the learner has already spent roughly two weeks learning contemporary AI-assisted engineering through real projects.

The project therefore has two jobs at once:

1. preserve what actually happened before memory smooths it into a cleaner story; and
2. avoid mistaking one unusually intense learner trajectory for a universal beginner path.

This baseline is intentionally provisional. It records the strongest current reconstruction and identifies where later source reconciliation is still needed.

## 2. Learner baseline

The primary observed learner reports beginning serious contemporary AI-assisted engineering in approximately late August 2026.

Relevant background:

- not an AI/software-industry professional;
- basic programming familiarity;
- historical Pascal experience approximately 35 years earlier;
- no recent professional software-engineering background;
- learning primarily by trying to build useful and increasingly sophisticated real systems with AI assistance.

This makes the case useful but atypical. The learner is neither an industry engineer nor a true blank slate.

## 3. Reconstructed development sequence

### Phase A — real project first, educational project later

The learner did not begin by taking a structured AI course. The learning environment emerged from attempting real project work, especially S.W.A.R.M., and discovering the knowledge required to make the work reliable.

This matters because many of the strongest candidate lessons were encountered as operational problems before they were recognized as educational concepts.

### Phase B — W.I.S.D.O.M. feasibility emerges

By 2026-08-27, W.I.S.D.O.M. was being investigated as a possible practical course built from the accumulated S.W.A.R.M. evidence corpus.

The initial research boundary was explicit: assess feasibility, documentation sufficiency, blind spots, and the lightest future observation process; do not yet build the course or modify the source project for educational convenience.

Early corpus assessment found unusually strong material around authority/source-of-truth, AI delegation, repository/worktree isolation, tests versus actual behavior, independent review, correction cycles, context management, provenance, recovery, credentials, and multi-agent orchestration. It also exposed weaker evidence around ordinary beginner debugging, dependencies, code reading, routine successes, quantified efficiency, and validation with additional learners.

### Phase C — learner goals and theory/practice become separate design questions

Around 2026-09-01, two important architecture questions separated:

- W.I.S.D.O.M. should reason backward from what a learner wants to accomplish with AI rather than prescribe why the learner wants AI.
- Theory and practice need an explicit bridge: understanding inference and AI behavior is not the same instructional problem as opening an account, creating a repository, using a terminal, or operating a tool.

Possible course tracks and learner segments were discussed, but remain hypotheses rather than adopted structure.

### Phase D — project work generates dense evidence

From roughly 2026-09-03 through 2026-09-06, active S.W.A.R.M. and G.A.M.E. work generated concentrated evidence about:

- authority and delegated autonomy;
- proposal versus authorization versus execution versus result;
- durable candidate/review/promotion lanes;
- free/external compute and economic authority;
- telemetry and claim calibration;
- operator control surfaces;
- artifact custody and handoff completeness;
- cross-project contamination boundaries;
- governance recursion and minimum sufficient governance;
- deterministic mechanisms replacing repeated prose reasoning;
- source-library provenance and independent research;
- parallel work and synchronization burden.

G.A.M.E. repository history during this period records Ground Zero doctrine, telemetry, free-compute work, durable candidate review, Operator Control Plane work, source-library foundation, governance research, and later product/design foundation freezes.

S.W.A.R.M. repository history records durable work/proposal work and a 2026-09-06 constitutional-governance closeout. That closeout preserves a governance-branching frontier: governance is useful while it narrows behavior; past a frontier it can create more branching, exceptions, and recursive administration than it removes.

S.P.A.R.K. contributed a different class of evidence: refoundation, takeover/handoff, convergence with G.A.M.E., and then an explicit park state rather than indefinite continuation.

## 4. Candidate learning themes emerging from history

These are research findings or hypotheses, not curriculum commitments.

### 4.1 Architecture before accidental complexity

The learner repeatedly encountered situations where deciding authority, state ownership, project boundaries, evidence standards, or workflow structure before implementation reduced later confusion.

This supports investigation of "architecture before code" as a compute/error-reduction strategy, but not as an absolute rule that every tiny task needs heavy architecture.

### 4.2 Evidence is not authority

A model response, review result, telemetry record, test pass, or outside consultation can supply evidence without gaining the power to decide project truth.

This distinction recurs across governance, review, experimentation, and project coordination.

### 4.3 Project state needs durable memory

Conversation alone proved too fragile for long-running, parallel work. Git history, provenance, explicit handoffs, and durable records became part of the learning process rather than mere administrative overhead.

### 4.4 Tool operation is part of the engineering problem

A technically correct plan can fail at the operator interface: wrong working directory, long terminal pastes, commands that launch an unexpected GUI, scripts that are safe in a file but hostile when pasted interactively, or validation rules that are inappropriate for immutable source artifacts.

The interface between reasoning and execution deserves explicit study.

### 4.5 Claims need calibration to evidence

Several project episodes showed pressure to infer more than telemetry or tests actually proved. The useful habit is to separate observed, inferred, assumed, attempted, completed, and verified states.

### 4.6 More governance is not always more control

The governance work produced a strong two-sided hypothesis: under-governance can leak authority or lose truth, while over-governance can create branching, recursive procedure, operator burden, and context cost.

### 4.7 Repeated reasoning is a tooling signal

When the same bounded decision recurs and can be resolved deterministically, it may belong in a validator, state lookup, policy engine, schema, preflight, or other tested mechanism rather than repeated model judgment.

### 4.8 Preserve what is already known to work

A recurring operator concern is that agents waste context and lose the thread by repeatedly re-proving already validated facts.

A current research hypothesis is therefore:

> preserve confirmed-working state as a stable baseline; focus new reasoning on unresolved, changed, contradicted, or failed portions unless prior evidence is invalidated.

This needs testing because stale assumptions can also become dangerous if "confirmed" state is never revalidated when its dependencies change.

## 5. Current user-research limitation

W.I.S.D.O.M. currently has one unusually rich longitudinal learner case and a large project-evidence corpus.

That is enough to discover candidate problems and methods. It is not enough to establish how common those problems are among beginners generally.

Market segmentation, learner archetypes, accessibility, pacing, motivation, and transfer to less ambitious goals remain separate research questions.

## 6. Current evidence gaps

The strongest gaps remain:

- ordinary beginner debugging rather than advanced project incidents;
- dependency/package/environment setup learning;
- learning to read unfamiliar code;
- examples where the simple path worked immediately;
- quantified time/cost savings or losses;
- independent learners with different backgrounds and goals;
- evidence about how much governance/architecture material a beginner can absorb before it becomes counterproductive;
- direct testing of teaching tone, humor, callouts, exercises, and retention.

## 8. Research rule going forward

Do not clean up the story before studying it.

Failures, awkward operator steps, mistaken assumptions, weird tool behavior, false starts, over-engineering, under-engineering, and recoveries are often more educationally valuable than the final polished artifact.
